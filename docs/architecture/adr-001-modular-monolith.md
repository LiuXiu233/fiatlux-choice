# ADR-001：采用模块化单体

状态：已接受

日期：2026-07-18

决策范围：V1 及可预见的 1–2 人运营阶段

## 背景

FIAT LUX CHOICE 同时覆盖公司治理、项目执行、合规、合同、财务、产品、审批和 AI 审计。这些模块有大量需要同一事务完成的动作，例如角色变更与审批、顾问运行与上下文快照、外部动作与人工批准。

目标团队只有 1–2 人。其主要约束是维护时间、部署可靠性、数据一致性和合规可追溯性，而不是独立团队并行发布或超大规模流量。

系统仍需要前端、同步 API 和后台任务的运行时分离，也需要为对象存储、LLM、GitHub 和未来外部接口保留标准适配器边界。

## 决策

采用 TypeScript monorepo 中的模块化单体：

- 一个 React/Vite Web 应用。
- 一个 Fastify API。
- 一个 pg-boss worker。
- 一个 PostgreSQL 业务数据库和队列 schema。
- 一个 S3 兼容对象存储。
- contracts、domain、db 和 integrations 共享包。
- Compose/Caddy 作为内网部署单元。

模块通过进程内领域 API、数据库事务和后台队列协作，不使用模块间 HTTP。外部供应商只能通过 integrations 中定义的端口接入。

## 约束

- 所有组织业务表必须有明确组织作用域或通过受控关系获得作用域。
- 领域规则不能只存在于前端。
- 高风险外部动作必须经过审批状态机。
- 长任务必须进入 worker。
- 适配器不能把外部“请求已发送”解释为“业务已完成”。
- 新模块必须有权限、审计、迁移和测试。
- 禁止为追求形式上的服务数量复制数据库或引入分布式事务。

## 后果

### 正面

- 关键业务和审计可以在一个 PostgreSQL 事务中提交。
- 本地开发、CI、部署、备份和恢复所需组件较少。
- 1–2 人团队可以理解并运营整套系统。
- 共享契约与领域规则减少前后端和 worker 漂移。
- 未来仍可按有证据的边界拆分。

### 负面

- API 和 worker 共享发布节奏与数据库 schema。
- 单个数据库是主要故障域，需依靠备份、恢复和主机控制管理风险。
- 不良模块纪律可能让代码耦合，需要依赖方向和评审约束。
- worker 与 API 竞争数据库资源，需监控连接和慢查询。
- 不能按模块独立选择不同数据技术。

## 被否决的方案

### 微服务

否决原因：需要服务发现、网络认证、分布式追踪、消息一致性、多个部署单元和跨服务恢复。当前团队规模和负载没有证据支持这些成本。

### 单进程全栈应用

否决原因：模型调用、备份和扫描等长任务会影响请求延迟；Web 静态资源、同步 API 和后台任务需要不同生命周期。

### 纯 SaaS / serverless 组合

否决原因：内网部署、数据地域、可恢复性、对象存储和后台任务边界更难统一验证，并增加供应商依赖。

### 仅使用电子表格和通用聊天

否决原因：无法稳定提供组织级权限、状态机、追加审计、模型上下文证据和恢复演练。

## 重新评估触发条件

出现以下任一证据时重新评估：

- 持续超过 50 名活跃用户或出现多个独立业务团队。
- 某一模块需要独立发布和独立 on-call。
- 某类任务的吞吐或故障显著影响其他模块。
- 法规或客户要求独立数据存储、密钥和保留策略。
- 单数据库无法满足经测量的性能或恢复目标。

重新评估不等于立即拆分。先通过模块边界、独立队列、连接池、读模型或部署副本解决，并用测量结果记录新的 ADR。
