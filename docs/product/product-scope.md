# FIAT LUX CHOICE 产品范围

文档状态：V1 候选范围

基准日期：2026-07-19

适用对象：耀光（广州）电子竞技有限公司及类似的中国境内 1–2 人公司

## 1. 产品目标

FIAT LUX CHOICE 是内部公司治理与运营系统。它把极小团队每天需要维护的目标、任务、决策、义务、合同、现金、风险、文件和审批放在同一套可审计工作流中，并让七类 AI 顾问在明确的数据权限内给出结构化分析。

它要解决的不是“再做一个企业聊天框”，而是以下三个经营问题：

1. 让负责人随时知道公司现在必须做什么、何时做、由谁负责、依据是什么。
2. 让高风险动作在执行前经过人工判断，执行后留下真实凭证。
3. 让 1–2 人团队用尽量少的重复录入维持治理、交付、现金流和合规连续性。

## 2. 产品原则

- 单一事实来源：同一事项只在一个主记录中维护，其他模块通过引用、任务或审计事件关联。
- 默认人工批准：银行付款、税务申报、发票红冲、合同正式签署、合同终止、人事处分、关键权限修改和对外法律承诺不能由系统或模型自行完成。
- 外部状态真实：manual 和 mock 适配器不得生成“已成功”假象；确认状态必须有外部回执证据。
- 权限先于便利：前端隐藏仅用于体验，所有访问控制必须由 API 根据组织和权限再次执行。
- 可追溯 AI：问题、上下文快照、提示词版本、模型调用、工具取数、引用、结果和人工修改均进入审计链。
- 政策可维护：法规政策作为带来源、适用条件、核验时间和人工复核状态的数据维护，不固化为永久业务常量。
- 模块化单体优先：前端、API、后台任务分离部署，领域与数据仍在一个可事务化的单体边界内。
- 内网优先：V1 面向受控办公内网，不以公网 SaaS 为默认威胁假设。

## 3. 目标用户与运行模式

| 用户 | 主要责任 | 推荐使用方式 |
| --- | --- | --- |
| 公司负责人 | 优先级、风险接受、关键审批、现金连续性 | 每日看经营工作台；每周复核目标、现金流和高风险事项 |
| 运营成员 | 项目、任务、合同准备、机会和资料维护 | 按业务发生录入；所有记录保留负责人、状态和下一动作 |
| 外部专业顾问 | 法务、财税、安全或专项复核 | 原则上授予 viewer 或最小自定义权限；不共享 owner 账号 |
| 系统管理员 | 成员、角色、集成、部署、备份恢复 | 与日常业务身份分离；关键权限变更走审批 |

对只有一名实际操作者的公司，系统仍保留申请与批准边界。应优先邀请一名受信任的第二审批人；确实无法双人复核时，使用明确记录的单人例外、补充复核和事后检查，不得使用共享账户绕过控制。

## 4. V1 功能范围

以下“已实现”指仓库中存在前端/API/数据或后台任务实现，不等同于已在生产环境验证。实际验收状态见[验收矩阵](../delivery/v1-acceptance-matrix.md)。

| 领域 | V1 能力 | 主要边界 |
| --- | --- | --- |
| 身份与组织 | 邮箱密码登录、组织成员、会话、角色权限、首次强制改密、停用/离职/重新启用审批 | 未提供企业 SSO、MFA、自助找回、恢复码或管理员受控重置密码 |
| 审计 | 组织级追加审计、请求 ID、前后值、操作者、IP 和 User-Agent | Docker 主机或数据库超级管理员仍属于高权限信任边界 |
| 文件 | 元数据、分类、扩展名—声明 MIME allowlist、上传前 UTF-8/JSON/格式信封/OOXML 结构与活动条目门禁、大小与 SHA-256、私有对象存储、审计下载和归档 | 完整 PDF/图片/Office 语义解析、病毒查杀、沙箱与 DLP 适配器尚未纳入 V1 |
| 执行管理 | 目标、项目、任务、决策 | 不是复杂项目排程或工时计费系统 |
| 治理合规 | 公司义务、合规日历、合规知识库、风险、合同 | 系统不替代律师、会计师或政府系统 |
| 简易财务 | 收支、发票、现金流预测与实际 | 不是法定总账、报税或银行核心系统 |
| 产品增长 | 产品组合、市场机会、电竞教育工作台、成人试点课程包、GitHub 技术情报 | 官网发布、学员门户、营销自动化和真实 GitHub 同步需独立适配 |
| 协作 | 审批、通知、工作流 | V1 通知以站内为主；邮件和 webhook 投递未配置 |
| AI 顾问 | 七类权限感知顾问、结构化输出和完整审计 | 默认 mock 仅用于演示；真实模型需完成供应商和数据审查 |
| 运维 | 健康检查、迁移、日志、Compose、备份与恢复脚本、CI | 生产启动和恢复演练必须有本环境证据后才能验收 |
| 客户端 | 响应式 Web、桌面/移动导航、PWA manifest 和 service worker | PWA 不缓存公司 API 数据，不提供完整离线业务编辑 |

## 5. 核心业务闭环

V1 必须支持以下闭环，而不是只展示列表：

1. 从公司目标建立项目和任务，更新进度并记录重大决策。
2. 从官方合规来源完成人工复核，形成义务、截止日、负责人和风险处置。
3. 建立合同及附件，完成人工审阅；正式签署通过高风险外部动作和回执闭环。
4. 记录收入、支出、发票和现金预测；付款、申报和红冲在批准后由人工外部执行。
5. 从市场机会形成产品或项目，按下一动作持续推进。
6. 选择权限范围内的公司记录发起 AI 顾问分析，核对证据并保留人工修改。
7. 从待审批事项完成批准或驳回；外部执行与系统批准保持不同状态。
8. 完成部署、健康检查、加密备份、独立恢复演练和回滚证据归档。

详细操作见[核心业务操作手册](../user/core-workflows.md)。

## 6. 明确不在 V1 内

- 自动操作银行账户、电子税务局、发票平台、电子签章、人事处分或对外法律承诺。
- 用 AI 输出代替法律、税务、审计、医疗、教育资质或劳动用工专业意见。
- 公网多租户 SaaS、跨地域高可用、零停机数据库切换。
- 法定会计总账、工资薪酬、社保公积金申报和全量 ERP。
- 面向学员的 LMS、直播课堂、在线考试、支付结算和大规模内容分发。
- 自动认定政策适用、自动计算易变税率或地方申报日期。
- 未经人工确认把官网、GitHub、上传文件或模型生成内容当作公司事实。

## 7. 关键假设

| 假设 | 默认值 | 需要重新评估的触发条件 |
| --- | --- | --- |
| 团队规模 | 1–2 名高信任操作者 | 超过 5 名活跃用户或出现独立部门 |
| 部署位置 | 中国境内受控办公内网 | 公网开放、跨境访问或外包托管 |
| 法人实体 | 单一中国境内公司 | 多公司、多法域或集团合并报表 |
| 财务复杂度 | 管理台账和现金预测 | 需要法定总账、自动报税或多币种核算 |
| 文件规模 | 单文件不超过 50 MB | 大量视频素材、长期媒体资产或 CDN |
| 模型使用 | 显式选取上下文，人工复核结果 | 自动批处理、敏感个人信息或跨境模型 |
| 可用性 | 单主机，可接受计划维护 | 业务要求 7×24 或分钟级灾备 |

假设变化时，应先更新威胁模型、权限矩阵、合规适用性和架构决策，再扩展功能。

## 8. V1 完成定义

只有同时满足以下条件才能把版本标记为 V1 完成：

- 核心闭环在真实 PostgreSQL、对象存储、API、worker 和 Web 组合环境端到端通过。
- 桌面和移动端无阻断缺陷，PWA 可安装且不会离线泄露业务数据。
- RBAC、组织隔离、审计、人工审批和外部回执状态得到集成与端到端验证。
- 七类顾问可用且完整记录提示词、模型、工具、引用和人工修改；真实模型边界经批准。
- lint、类型检查、单元、集成、端到端和生产构建全部通过。
- 生产 Compose、迁移、健康检查、日志、升级、回滚、备份和独立恢复均有实际证据。
- 合规来源已按适用性完成必要人工复核，未复核来源不会进入确定性建议。
- 仓库完成密钥扫描且不包含真实凭据、个人信息或生产数据。
- 所有已知缺陷均已关闭，或经负责人书面接受且不阻断核心使用。

在验收矩阵仍有“待验证”或“阻断”项时，只能称为 V1 候选版本。
