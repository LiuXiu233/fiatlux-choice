# 角色与权限使用指南

## 1. 权限模型

FIAT LUX CHOICE 的权限由“组织成员关系 + 一个或多个角色 + 权限字符串”组成。API 从当前会话确定 userId 和 orgId，不接受客户端自行指定公司作用域。

权限格式为 资源:动作，例如 tasks:read、contracts:update。资源通配符如 tasks:* 表示该资源的全部动作；全局通配符 * 仅授予 owner。

前端根据权限隐藏菜单或操作按钮，但这不是安全边界。API 会在每个受保护路由再次检查权限，并在数据查询中强制加入 orgId。

## 2. 系统角色

下表描述种子数据中的默认角色。实际有效权限以系统“成员与权限”及 GET /api/v1/roles 返回值为准。

| 角色 | 适用人 | 主要能力 | 关键限制 |
| --- | --- | --- | --- |
| owner | 公司最终负责人 | 全部权限，包括系统管理和审批 | 权限最大；至少保留一个 owner，不应用于外部顾问 |
| admin | 受信任管理员 | 业务全模块、成员管理、审批、集成测试、备份 | 没有全局通配符；应与日常低权限账号分离 |
| member | 日常运营成员 | 项目、任务、决策、风险、产品、机会和顾问运行；读取合同财务合规 | 不能管理用户、角色、备份或修改大多数敏感台账 |
| viewer | 只读观察者或外部顾问 | 读取经营、执行、治理、产品和顾问结果 | 默认看不到财务、发票、现金、文件和审计 |

member 的默认写权限集中在项目、任务、决策、风险、产品、机会和顾问运行；其通知权限只允许读取并标记本人通知，合同、财务、发票、现金流、义务和合规资料通常只读或有限更新。viewer 不是“所有内容只读”，而是只读一个经过限制的资源集合；通知同样只限本人。

## 3. 角色分配建议

### 两人团队

- 公司负责人使用 owner。
- 日常运营者使用 member；只有确需维护用户、财务或备份时再授予 admin。
- 高风险申请尽量由另一人审批，避免同一人申请和批准。

### 一人团队

- 保留唯一 owner，但不要创建共享管理员账号。
- 邀请外部会计、律师或受信任管理人作为最小权限第二审批人，是首选控制。
- 无法双人审批时，必须使用系统支持的显式单人例外确认，并记录原因、证据和后续复核人；具体可用性见[已知边界](../delivery/known-boundaries.md)。

### 外部顾问

- 优先使用 viewer 或后续建立的最小自定义角色。
- 不要通过导出全库、共享 owner 密码或转发会话 Cookie 提供资料。
- 任务结束后撤销成员关系或角色，并复核审计日志。

## 4. 默认权限摘要

| 资源组 | owner | admin | member | viewer |
| --- | --- | --- | --- | --- |
| 经营工作台 | 全部 | 读 | 读 | 读 |
| 目标 | 全部 | 全部 | 读、更新 | 读 |
| 项目、任务、决策 | 全部 | 全部 | 全部 | 读 |
| 义务 | 全部 | 全部 | 读、更新 | 读 |
| 合规知识和日历 | 全部 | 全部 | 读 | 读 |
| 风险 | 全部 | 全部 | 全部 | 读 |
| 合同 | 全部 | 全部 | 读 | 读 |
| 收支、发票、现金流 | 全部 | 全部 | 读 | 无 |
| 产品、市场机会 | 全部 | 全部 | 全部 | 读 |
| GitHub 情报 | 全部 | 全部 | 读 | 读 |
| 文件 | 全部 | 全部 | 读、创建 | 无 |
| 通知 | 跨收件人创建、查看、归档；本人标记已读 | 跨收件人创建、查看、归档；本人标记已读 | 读取本人、专用端点标记已读 | 读取本人、专用端点标记已读 |
| 工作流定义和运行 | 全部 | 全部 | 读 | 无 |
| 审批、外部动作 | 全部 | 全部 | 读 | 无 |
| 顾问 | 全部；可读取组织内运行，但仍受顾问与上下文权限约束 | 全部；具有 `advisor-runs:read-all`，但仍受顾问与上下文权限约束 | 使用顾问；只读取和修改本人发起且当前可访问的运行 | 仅读取本人发起且当前可访问的运行 |
| 审计 | 全部 | 读 | 无 | 无 |
| 用户、角色、集成、备份 | 全部 | 管理或读取 | 无 | 无 |

“全部”仍受组织隔离、记录状态、乐观并发版本和业务状态机约束。

通知有额外的收件人边界：member/viewer 的列表和单条读取由 API 强制限定 `recipientId` 为当前用户，不能读取或标记他人的通知；标记已读使用 `POST /api/v1/notifications/:id/read`，不是通用 PATCH。admin/owner 可跨收件人创建、查看和归档，但任何角色都不能 PATCH 已创建通知的标题、正文、收件人或投递事实。

顾问运行也有额外的发起人边界：默认只有 `requestedBy` 对应的用户可在列表、详情和人工修改接口访问该运行；member 没有 `advisor-runs:read-all`，因此不能读取或修改同事的运行。admin/owner 可凭 `advisor-runs:read-all` 或 `*` 跨发起人读取，但仍必须拥有该顾问的 requiredPermission，以及运行中每个上下文资源的 `资源:read` 权限；`read-all` 不是数据越权通行证。任一条件不满足时 API 返回 404，人工修改也使用同一可见性判断。

## 5. 成员入职

1. admin 或 owner 在“成员与权限”创建成员，使用唯一邮箱和至少 14 位临时密码。
2. 系统创建用户和 `pending` 成员关系，同时生成关键权限变更审批；角色不会静默生效。此时即使密码正确，登录也返回 403 且不创建会话。
3. 另一名有 approvals:approve 权限的用户核对人员身份、角色和原因后批准。
4. 批准后 membership 才变为 active 并取得角色；驳回时不得交付凭据。
5. 通过安全渠道交付临时凭据，新成员登录并确认组织、角色和菜单范围。
6. 新成员首次登录即带 `mustChangePassword`；改密前 API 只允许 `GET /auth/me`、`POST /auth/change-password` 和 `POST /auth/logout`。在“设置 → 登录密码”设置至少 14 位且不同于临时值的新密码，成功后保留当前会话并撤销其他会话。
7. 用一个应允许和一个应拒绝的动作验证权限，保存审计证据。

当前版本已强制首次改密，但仍没有自助密码找回、恢复码、管理员密码重置和 MFA。管理员必须在上线前建立线下身份核验与密码恢复流程。

首次 seed 是仅用于空组织引导的**非日常运维命令**。显式 `SEED_MODE=bootstrap` 新建 bootstrap user、active membership、owner assignment、四个内置角色及完整权限基线；遇到既有组织 slug 会失败，不会偷偷转为维护。只有该模式接受 admin name/password。首次 owner 同样设置 `mustChangePassword`，必须按[内网部署手册](../admin/intranet-deployment.md#5-首次启动与初始化)完成首次登录和改密。不得把 seed 放入普通启动、重启、升级或定时任务。

既有组织只能显式使用 `SEED_MODE=metadata-only`。它不接受或读取 admin name/password，不更新组织名或任何用户/membership 字段，不创建 membership，不补系统角色/权限，也不恢复任何已移除的 owner 或其他 role assignment。该模式只补齐缺失的七类内置顾问提示词 v1；每个实际新增版本都会记录 system actor、seed mode、版本和提示词 SHA-256 的追加审计及 metadata requestId，既有版本不覆盖。它还导入或更新官方合规来源目录的标题、分类、发布机关、来源日期、来源元数据、元数据哈希和监测节奏；既有人工 review/status/verified 事实不会被普通覆盖，检测到来源元数据变化时会标记 stale/uncertain 供人工复核。

内置角色/权限升级属于关键权限变更，只能在人工批准后显式选择 `SEED_MODE=system-role-maintenance`，并同时提供本组织 active owner 的 `SEED_MAINTENANCE_OPERATOR_EMAIL`、非空 `SEED_MAINTENANCE_REASON`、`SEED_MAINTENANCE_APPROVAL_REFERENCE` 和唯一 `SEED_MAINTENANCE_REQUEST_ID`。该模式拒绝任何 bootstrap/admin 身份字段，只增加代码基线中缺失的内置角色/权限，不删除额外权限，也不触碰 membership/assignment；每项新增都以该 owner 为 actor，在同一事务写 before/after、原因、批准/变更编号和 requestId 的追加审计。缺少参数、operator 不是 active owner、组织不匹配或仍注入引导密码时必须失败关闭。

唯一 owner 忘记密码不应通过 seed、改库或新增 API 绕过。受支持的最小恢复仅为生产主机上的离线 one-off CLI：精确匹配组织 slug 和小写 email，确认目标 membership 与 owner role 均为 active/未归档，要求固定生产确认、reason、人工批准/变更编号和唯一 requestId，并只从 stdin/secret 接收 14–256 字符且不同于旧值的临时密码。成功事务会使用 Argon2id 更新、设置 `mustChangePassword=true`、撤销该用户全部会话并追加不含密码的审计；首次临时登录仍受三端点限制，必须立即改密。完整 Compose 命令见 [README 的唯一 owner 离线恢复](../../README.md#唯一-owner-离线恢复)。

## 6. 角色变更、停用与离职

角色分配和移除必须通过“关键权限修改”审批：

1. 申请人先读取最新成员关系，选择 `membershipId`、`roleId`、assign 或 remove，并提交当前 membership 的 `expectedVersion`、本次唯一 `idempotencyKey` 和业务原因。
2. 系统创建 critical 风险审批，不立即修改 membership_roles；审批载荷会保存成员版本快照和幂等键。
3. 审批人核对最小权限和职责分离后批准或驳回。
4. 批准时系统重新锁定并核对 membership 版本、当前角色关系以及目标角色；任一事实已变化即返回冲突，不执行陈旧审批，申请人须读取新版本后重新申请。
5. 通过复核后，角色变更、membership 版本递增和审计事件在同一数据库事务中写入；重复请求依靠幂等键识别，不能通过重试重复变更。
6. 移除 owner 时还会在批准事务中重新核对最后一个 active owner，系统拒绝移除最后一个 owner。
7. 旧审批若缺少 `expectedVersion` 或 `idempotencyKey` 会失败关闭，不能直接批准；应驳回旧审批并按当前版本重新申请。

成员停用、重新启用和离职使用独立的人工审批闭环，不能用编辑姓名或直接改数据库代替：

1. 在“成员与权限”打开有效成员的更多操作，选择“申请停用”或“申请离职”，填写交接、复核或外部权限回收安排。
2. 系统创建 `critical` 审批；列表显示“待审批：停用/离职”，但成员仍为 `active`，现有会话也不会在申请阶段被静默撤销。
3. 审批人到“审批中心”核对理由。驳回只改变审批状态，不改变成员或会话；批准时系统重新核对成员状态和版本。
4. 批准成功后，系统在同一数据库事务中把本组织 membership 改为 `inactive`（停用）或 `offboarded`（离职），并撤销该用户在本组织的全部未撤销会话。用户在其他组织的 membership、角色和会话保持不变，全局用户状态也不会被误停用。
5. 如果成员在申请后已被修改、申请已处理或不再有效，审批返回冲突并保持原状态；应重新读取最新成员版本并发起新申请。
6. 系统拒绝停用、离职或移除最后一个“未归档且 active”的 owner。已停用、已离职或已归档成员即使保留历史 owner 角色，也不能满足最后 owner 要求。
7. 审计日志分别保存申请、批准/驳回、成员状态变化和会话撤销数量，不保存 session token。完成后还要人工回收邮箱、GitHub、银行、税务、签章等本系统之外的权限，并记录外部证据。

重新启用只适用于 `inactive` 且至少保留一个未归档角色的成员：在更多操作选择“申请重新启用”，经 `critical` 审批后恢复为 `active`。批准不会复活任何旧会话；成员必须用现有凭据重新登录，系统才会创建新会话。驳回、陈旧审批或无有效角色都保持 `inactive`。`offboarded` 成员不能直接重新启用，必须等待未来的重新入职流程重新核验身份、合同、职责和角色，当前版本不得用直接改库绕过。

优先由另一名审批人复核。单人团队确需申请人自批时，仍沿用显式 `SELF_APPROVAL_ACKNOWLEDGED` 补偿控制和事后独立复核，不能省略申请与批准两个步骤。

## 7. 顾问权限是双重边界

调用 AI 顾问必须同时满足：

- 用户是该运行的发起人，或者拥有 `advisor-runs:read-all` / `*`。
- 用户具备该顾问的 requiredPermission。
- 用户能读取所选记录。
- 顾问策略允许读取该资源类型。

例如，财务顾问可以读取收支、发票、现金流、合同和目标；但发起者没有 financial-entries:read 时，不能把收支记录加入上下文。admin 即使可以跨发起人查看运行，若缺少该顾问入口权限或其中某类上下文的读取权限，该运行仍按 404 不可见。顾问不能扩大用户权限，也不会自动扫描整个公司数据库。

完整范围见[AI 顾问与审计](./ai-advisors-and-audit.md)。

## 8. 权限复核清单

每月或人员变化后执行：

- 每个活跃成员都能对应到真实人员和当前职责。
- owner 数量合理，最后一个 owner 有恢复安排。
- admin 只授予需要管理职责的人。
- 外部顾问权限和结束日期仍然必要。
- 最近的角色变更都有审批、理由和审计记录。
- 离职人员会话与外部集成凭据已经撤销。
- 抽查跨组织、财务、文件、审计和审批的拒绝结果。

发现异常权限时，先保全审计证据，再按批准流程修正；不要直接修改数据库。
