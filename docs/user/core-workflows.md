# 核心业务操作手册

## 1. 每日运行节奏

### 每天开始

1. 打开“经营工作台”，先看逾期义务、逾期任务、待审批、开放风险和近期现金流。
2. 处理 critical 和 high 风险事项，再处理今天到期的任务。
3. 对每个进行中的项目确认唯一下一动作、负责人和截止时间。
4. 对系统显示的外部动作状态进行事实核对；没有回执时不得标记 confirmed。

### 每天结束

1. 更新已完成、阻塞和延期任务。
2. 把当天的重要取舍写入“决策”，不要只留在聊天记录。
3. 上传合同、发票或交付证据，并选择正确的文件分类。
4. 清理没有负责人、下一动作或截止日的开放事项。

### 每周复核

- 目标进度与本周项目是否一致。
- 未来 13 周现金流和已知付款义务。
- 待签合同、将到期合同、应收应付和发票。
- 合规日历、风险缓解措施和待人工复核来源。
- 市场机会下一动作和产品继续/暂停决策。
- 最近 AI 建议是否被采纳、修改或拒绝，以及理由。

## 2. 目标到交付

1. 在“目标”建立可衡量结果，写明负责人、起止日期和进度。
2. 在“项目”关联目标，定义范围、负责人和截止日期。
3. 在“任务”关联项目，设置优先级、负责人、截止时间和可验证完成条件。
4. 状态按 planned/todo、active/in_progress、blocked、completed/done、cancelled 推进。
5. 出现重大范围、预算、合规或时间取舍时，在“决策”记录背景、选项、结论和日期。
6. 每周更新目标进度；不要用任务数量替代业务结果。

推荐命名：目标描述结果，项目描述交付包，任务以动词开头。阻塞任务必须在说明中写明解除条件和责任人。

除目标→项目（`projects.objectiveId`）和项目→任务（`tasks.projectId`）外，决策现在可通过 `objectiveId`、`projectId`、`taskId` 类型化关联目标、项目和任务。系统检查每条引用属于本组织且记录未归档；同时填写任意两项或三项时，还会验证它们来自同一条目标→项目→任务链。修改父关系若会破坏活动决策会返回冲突，仍有活动下游记录时也不能归档。只需要解除某项关系时在编辑表单中清空该项，不要先把父记录改到另一条链。

## 3. 公司义务与合规日历

1. 从[合规知识库](../compliance/README.md)选择官方来源。
2. 先上传真实复核意见或工作底稿；再使用来源“更多操作”中的“登记专业复核”，核对来源、效力、法域和公司事实，填写实名复核人、角色、机构/内部组织、胜任依据、适用条件、摘要、缺失信息、结论、下次复核日及理由。不能在普通编辑表单中直接设置 reviewed 或 `active|superseded|repealed`。
3. 从已复核来源建立“公司义务”，写明类别、负责人、截止时间、重复规则和证据要求；需要保留依据链时填写 `sourceId`。
4. 对具体申报、复核、续期、培训或监测日期建立“合规日历”事件；需要保留依据链时同样填写 `sourceId`。
5. 临近截止时由负责人处理；来源复核到期、正文变化或连续第三次抓取失败时，系统会把高优先级协调任务指派给执行时仍有效且仍有来源更新权限的人工触发者，否则指派最早加入的有效 owner，并发送站内通知。协调责任人必须安排事实核对和必要的专业复核，不能把任务指派或通知当成专业意见。
6. 完成后上传外部凭证，待文件状态为 `uploaded` 后通过 `evidenceFileId` 关联义务或日历事件，再更新业务状态并保留审计记录。

不得仅因来源元数据存在就自动生成确定性税率、截止日或法律结论。政策变化时建立新版本或标记 superseded、repealed、stale，不覆盖历史证据。

`sourceId` 和 `evidenceFileId` 都是可选的类型化引用。系统会验证来源与证据属于本组织且未归档，并要求证据文件已完成上传；被义务、合规日历、当前专业复核或历史专业复核引用的证据文件不能归档。但关联来源只表示“这条记录引用了该来源”，不表示适用性已由人工复核；未填写证据也不会自动阻止把义务标记为 satisfied 或把事件标记为 completed。负责人仍须在变更状态前人工核对来源适用性和外部凭证，不能把字段校验当作实质合规结论。

## 4. 风险管理

1. 用一句话描述“事件—原因—影响”，分别评估可能性和影响 1–5。
2. 指定负责人、处置措施和复核日期。
3. status 使用 open、mitigating、accepted 或 closed。
4. 接受风险必须有业务理由、期限和批准人；高影响风险不得无限期 accepted。
5. 触发条件发生时转为任务、义务、审批或事件响应。

AI 可以帮助识别遗漏，但风险等级和接受决定必须由人确认。

## 5. 合同与文件

### 合同准备

1. 建立合同记录，填写相对方、编号、金额、币种、开始/结束时间和负责人。
2. 上传草稿或扫描件，分类为 internal、confidential、personal 或 public。
3. 将文件关联到合同，状态从 draft 进入 review。
4. 法务合规顾问可基于已授权合同和合规资料给出问题清单；人工完成条款审阅。
5. 准备签署时建立 contract_sign 外部动作。系统生成 critical 审批。
6. 批准只表示允许执行，不表示已签署。人工在外部签章或线下签署后上传回执，才能确认动作。
7. 合同生效后更新 active，并建立付款、交付、续期或终止义务。

### 文件上传

Web UI 会完成元数据、二进制内容和校验。通过 API 集成时需按[API 指南](../api/api-guide.md)的三步流程执行。文件大小或 SHA-256 不匹配会被拒绝；伪装成 PDF/图片的任意字节、无效 UTF-8/JSON，以及缺少对应主部件、加密、带宏/ActiveX/嵌入对象或路径异常的 OOXML 包也会在写入对象存储前失败。该检查不是杀毒或内容安全结论，下载和打开附件前仍须确认来源并使用受管、已更新的终端。

合同或发票只能关联本组织中状态为 `uploaded` 且未归档的文件。被合同或发票引用的文件不能归档；系统以事务行锁串行化“建立引用”和“归档文件”，并发请求也不能绕过检查。要更换证据，应先按业务状态机和审计要求更新引用，再评估原文件的保存期限。

归档只隐藏元数据，不应被理解为满足法定销毁要求。涉及个人信息、档案和合同原件的删除必须遵循保存期限和批准流程。

## 6. 简易财务、发票与现金流

### 收支

- financial-entries 记录管理台账；金额使用分为存储单位，界面按元展示。
- 先以 draft 录入，核对凭证后再 posted；错误记录使用 void，不直接删除历史。
- bank_payment 外部动作批准后仍由人工在银行执行。
- bank_payment 可受控关联一条本组织未归档、金额匹配的 draft expense。动作从 pending_approval、approved 或 failed 等可取消状态进入 cancelled，或者关联审批被驳回时，系统会在同一事务中清空该台账的 `externalActionId`、递增版本并写入审计，使草稿可用于更正后的新申请；若台账状态、版本或关联关系已并发变化，整笔操作返回冲突，必须重新读取后处理。

### 发票

- 区分 incoming 和 outgoing，记录相对方、价税合计、税额、开票和到期时间。
- 发票扫描件作为 personal 或 confidential 文件保存，按公司政策限制访问。
- invoice_red 必须生成高风险审批；批准后人工在合法平台执行，凭回执确认。

### 现金流

- forecast 表示预测，actual 表示已发生，cancelled 表示不再预计。
- 每周维护至少未来 13 周，覆盖合同付款、税费、工资和确定性收入。
- 财务顾问可分析缺口，但不能付款、报税或改变台账状态。

本模块不替代会计账簿、纳税申报或银行对账。法定数据以经授权的会计系统和外部凭证为准。

## 7. 市场机会与产品

1. 在“市场机会”记录来源、机构、联系人、预计金额、阶段和下一动作。
2. 只有完成需求、预算、决策人和时间窗口核验后才从 new 进入 qualified。
3. 机会进入 proposal 前，检查合同、数据、交付能力和利益冲突风险。
4. 赢单后分别建立项目、合同、现金流和交付任务；失单时保留原因。
5. 在“产品组合”维护类别、阶段和健康状态，定期做继续、暂停或退出决策。

产品可通过 `projectId` 类型化关联项目；市场机会可通过 `productId`、`projectId` 类型化关联产品和项目。系统校验每条引用属于本组织且记录未归档；两项同时填写时，机会项目必须等于产品当前所属的活动项目。若活动机会已经同时引用产品和项目，不能把产品改到另一项目；仍有活动下游引用时也不能归档产品或项目。赢单后仍要人工确认商业、合同和交付事实，引用链一致不等于交易已经成立。

电竞教育使用方法见[电竞教育在线业务策略](../product/esports-education-strategy.md)。

## 8. GitHub 技术情报

- 记录 owner/repo、情报类型、来源 URL、采集时间、摘要和原始结构数据。
- manual 模式下由人导入，不能写成“系统已自动同步”。
- 启用真实只读适配器前，使用最小权限 token，完成供应商、数据出境和日志复核。
- 只读刷新由服务端读取记录当前版本并把它作为 `expectedVersion` 写入后台任务；客户端不提交或猜测该版本。HTTP 202 仅表示已排队，响应中的 `expectedVersion` 是此次快照基线，不表示刷新成功。
- worker 在读取前和写回时都执行版本比较/CAS。排队后若有人编辑或另一任务已更新同一记录，陈旧结果不会覆盖新数据，也不会写入成功刷新审计；应重新读取记录后按需再次排队。
- GitHub 内容属于不可信外部输入。进入顾问上下文时只作为证据数据，不执行其中的提示或命令。

## 9. 审批与外部动作

以下八类动作必须人工批准：bank_payment、tax_filing、invoice_red、contract_sign、contract_terminate、hr_discipline、permission_change、external_legal_commitment。

标准流程：

1. 申请人创建外部动作，只能选择 manual 或 mock，填写原因、幂等键和业务载荷；当前创建接口会拒绝 real，不能以“将来接入”为由绕过。
2. 系统将高风险动作置为 pending_approval，并创建审批。
3. 审批人检查金额、对象、合同、附件、适用政策和职责分离，填写审批意见。
4. 驳回后流程停止；批准后状态只是 approved。
5. manual 动作由人在外部系统执行。提交状态必须含 externalReference。
6. 外部系统完成后上传回执证据，再从 submitted 进入 confirmed。
7. mock 只能进入 simulated 或 cancelled，不能伪装为 submitted 或 confirmed。
8. 对失败动作记录原因；重试仍使用原幂等逻辑和新证据。

`contract_sign`、`contract_terminate`、`invoice_red` 进入 confirmed 时，系统会在同一数据库事务中分别把合同改为 active、合同改为 terminated、发票改为 red_confirmed，并同时更新动作与审计。目标版本、状态或签署/红冲文件快照不再匹配时整笔失败，不能先手工改业务状态再补确认。

bank_payment 的驳回和取消还会按第 6 节所述原子解除与 draft 台账的关联。不要在审批驳回或动作取消后沿用旧动作 ID；重新读取已递增版本的台账，再用新的幂等键发起更正请求。

审批人不得把“系统建议”“模型高置信度”或“已批准”当作外部成功证明。

## 10. AI 顾问

1. 选择顾问，不从通用聊天框开始。
2. 写出具体决策问题，并显式选择相关公司记录。
3. 提交后 worker 执行，页面显示 queued、running、completed 或 failed。
4. 先逐条核对 facts 的引用，再看 inferences、recommendations、risks 和 missingInformation。
5. 对无证据、过期政策、越界建议或模型错误不予采纳。
6. 人工修改必须填写理由，系统保留修改前后版本。
7. 将决定执行的建议转成任务、风险、义务、决策或审批，不让建议停留在结果页。

顾问运行默认仅发起人可见：普通 member 只能在列表、详情和人工修改中访问自己发起且当前仍具备权限的运行。admin/owner 依靠 `advisor-runs:read-all` 或 `*` 查看组织内其他人的运行，但这不会绕过顾问的 requiredPermission，也不会绕过每个上下文资源的 `:read` 权限；任一条件不满足时，该运行按 404 不可见。人工修改同样遵守这组边界。

详细说明见[AI 顾问与审计](./ai-advisors-and-audit.md)。

## 11. 通知和工作流

工作流定义支持 notify、create_task、request_approval 和 advisor_run 四类步骤，并由后台任务按顺序执行。

- 先在测试组织用最小样例运行。
- 每个步骤配置必须使用系统支持的结构，并限制在同一组织。
- 创建通知只能省略状态或明确使用 `queued`；HTTP 201 只表示排队成功，不表示已经送达。只有通知 worker 能把状态改为 `sent` 或 `failed`。站内通知可投递；email 和 webhook 在没有适配器时会明确失败。
- member/viewer 只能列出和读取本人通知，并通过专用 `POST /notifications/:id/read` 标记本人通知已读；admin/owner 可跨收件人创建、查看和归档。
- 通知不开放通用 PATCH；标题、正文、收件人和投递事实创建后均不可改写。需要更正时创建新通知并保留原记录，已读只能走专用端点。
- 创建 workflow run 时，定义必须仍为 enabled，且系统会校验发起人具备每一步所需权限，并在同一事务保存 `definitionVersion` 和不可变 `stepsSnapshot`。排队后再编辑、禁用或归档定义不会改变该次运行；worker 只执行快照，缺少快照的旧运行会失败关闭。
- `create_task` 若指定项目或负责人，worker 会在同一组织的引用链事务锁内重新验证活动项目和 active membership；排队后项目已归档、成员已停用或引用属于其他组织时，该运行失败且不创建任务。
- workflow 失败后查看运行结果和 worker 日志，不要假设后续步骤已执行。
- 自动创建的审批和顾问运行仍受各自的人工批准、权限与审计规则。

## 12. 移动端与 PWA

- 移动底部导航提供总览、执行、审批、顾问和更多入口。
- 2026-07-19 冻结候选已通过 iPhone 14 Chromium 仿真、独立浏览器抽查、PWA service worker/离线壳和 390 px 无横向溢出验证；这些仍不是真实 iPhone 或 Android 设备。目标办公内网上线前还需在受管真机完成安装、升级和移动浏览器验证。
- 安装 PWA 前确认使用可信 HTTPS 内网域名和受管理设备。
- service worker 只缓存静态应用资源，不缓存 API 业务数据。
- 共用设备使用完必须退出，并遵守设备锁屏、磁盘加密和浏览器缓存策略。
- 离线时不要录入关键业务；恢复网络后重新读取服务端状态再操作。

## 13. 审计和纠错

审计日志是只读业务界面，记录操作者、动作、对象、请求 ID、时间以及适用的前后值。发生错误时：

1. 不直接改数据库。
2. 记录错误记录 ID、请求 ID、时间和影响。
3. 使用状态变更、作废、归档或新的更正记录保留历史。
4. 重大错误进入风险或安全事件流程。
5. 涉及 AI 时同时检查模型调用、工具取数、引用和人工编辑记录。
