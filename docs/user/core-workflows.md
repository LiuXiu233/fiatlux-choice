# 核心业务操作手册

## 1. 每日运行节奏

### 每天开始

1. 打开“经营工作台”，先看逾期义务、逾期任务、待审批、开放风险和近期现金流。
2. 处理 critical 和 high 风险事项，再处理今天到期的任务。
3. 对每个进行中的项目确认唯一下一动作、负责人和截止时间。
4. 对系统显示的外部动作状态进行事实核对；没有回执时不得标记 confirmed。

### 每天结束

1. 更新已完成、阻塞和延期任务。
2. 把当天的重要取舍写入“决策”，不要只留在聊天记录。
3. 上传合同、发票或交付证据，并选择正确的文件分类。
4. 清理没有负责人、下一动作或截止日的开放事项。

### 每周复核

- 目标进度与本周项目是否一致。
- 未来 13 周现金流和已知付款义务。
- 待签合同、将到期合同、应收应付和发票。
- 合规日历、风险缓解措施和待人工复核来源。
- 市场机会下一动作和产品继续/暂停决策。
- 最近 AI 建议是否被采纳、修改或拒绝，以及理由。

## 2. 目标到交付

1. 在“目标”建立可衡量结果，写明负责人、起止日期和进度。
2. 在“项目”关联目标，定义范围、负责人和截止日期。
3. 在“任务”关联项目，设置优先级、负责人、截止时间和可验证完成条件。
4. 状态按 planned/todo、active/in_progress、blocked、completed/done、cancelled 推进。
5. 出现重大范围、预算、合规或时间取舍时，在“决策”记录背景、选项、结论和日期。
6. 每周更新目标进度；不要用任务数量替代业务结果。

推荐命名：目标描述结果，项目描述交付包，任务以动词开头。阻塞任务必须在说明中写明解除条件和责任人。

当前数据库只对目标→项目（`objectiveId`）和项目→任务（`projectId`）提供类型化引用。决策没有 objective/project/task 类型化字段；如需关联，应在决策背景中写相关记录 UUID 并人工核对。此临时做法不具备外键完整性，不能把它描述成完整的类型化“目标—项目—任务—决策”链。

## 3. 公司义务与合规日历

1. 从[合规知识库](../compliance/README.md)选择官方来源。
2. 先核对来源、效力、法域、公司事实和适用条件，把 reviewStatus 设为 reviewed，并仅在确认现行时使用 active。
3. 从已复核来源建立“公司义务”，写明类别、负责人、截止时间、重复规则和证据要求。
4. 对具体申报、复核、续期、培训或监测日期建立“合规日历”事件。
5. 临近截止时由负责人处理；系统逾期扫描只改变内部状态，不代表完成申报。
6. 完成后上传外部凭证，更新义务或日历状态，并保留审计记录。

不得仅因来源元数据存在就自动生成确定性税率、截止日或法律结论。政策变化时建立新版本或标记 superseded、repealed、stale，不覆盖历史证据。

## 4. 风险管理

1. 用一句话描述“事件—原因—影响”，分别评估可能性和影响 1–5。
2. 指定负责人、处置措施和复核日期。
3. status 使用 open、mitigating、accepted 或 closed。
4. 接受风险必须有业务理由、期限和批准人；高影响风险不得无限期 accepted。
5. 触发条件发生时转为任务、义务、审批或事件响应。

AI 可以帮助识别遗漏，但风险等级和接受决定必须由人确认。

## 5. 合同与文件

### 合同准备

1. 建立合同记录，填写相对方、编号、金额、币种、开始/结束时间和负责人。
2. 上传草稿或扫描件，分类为 internal、confidential、personal 或 public。
3. 将文件关联到合同，状态从 draft 进入 review。
4. 法务合规顾问可基于已授权合同和合规资料给出问题清单；人工完成条款审阅。
5. 准备签署时建立 contract_sign 外部动作。系统生成 critical 审批。
6. 批准只表示允许执行，不表示已签署。人工在外部签章或线下签署后上传回执，才能确认动作。
7. 合同生效后更新 active，并建立付款、交付、续期或终止义务。

### 文件上传

Web UI 会完成元数据、二进制内容和校验。通过 API 集成时需按[API 指南](../api/api-guide.md)的三步流程执行。文件大小和 SHA-256 不匹配会被拒绝。

归档只隐藏元数据，不应被理解为满足法定销毁要求。涉及个人信息、档案和合同原件的删除必须遵循保存期限和批准流程。

## 6. 简易财务、发票与现金流

### 收支

- financial-entries 记录管理台账；金额使用分为存储单位，界面按元展示。
- 先以 draft 录入，核对凭证后再 posted；错误记录使用 void，不直接删除历史。
- bank_payment 外部动作批准后仍由人工在银行执行。

### 发票

- 区分 incoming 和 outgoing，记录相对方、价税合计、税额、开票和到期时间。
- 发票扫描件作为 personal 或 confidential 文件保存，按公司政策限制访问。
- invoice_red 必须生成高风险审批；批准后人工在合法平台执行，凭回执确认。

### 现金流

- forecast 表示预测，actual 表示已发生，cancelled 表示不再预计。
- 每周维护至少未来 13 周，覆盖合同付款、税费、工资和确定性收入。
- 财务顾问可分析缺口，但不能付款、报税或改变台账状态。

本模块不替代会计账簿、纳税申报或银行对账。法定数据以经授权的会计系统和外部凭证为准。

## 7. 市场机会与产品

1. 在“市场机会”记录来源、机构、联系人、预计金额、阶段和下一动作。
2. 只有完成需求、预算、决策人和时间窗口核验后才从 new 进入 qualified。
3. 机会进入 proposal 前，检查合同、数据、交付能力和利益冲突风险。
4. 赢单后分别建立项目、合同、现金流和交付任务；失单时保留原因。
5. 在“产品组合”维护类别、阶段和健康状态，定期做继续、暂停或退出决策。

当前 products、opportunities 与 projects 之间没有类型化关联。建立这些记录后，在说明/标题中写对方 UUID，并在每周复核时人工确认一致；不要把同名记录或自由文本匹配当成数据库关系。

电竞教育使用方法见[电竞教育在线业务策略](../product/esports-education-strategy.md)。

## 8. GitHub 技术情报

- 记录 owner/repo、情报类型、来源 URL、采集时间、摘要和原始结构数据。
- manual 模式下由人导入，不能写成“系统已自动同步”。
- 启用真实只读适配器前，使用最小权限 token，完成供应商、数据出境和日志复核。
- GitHub 内容属于不可信外部输入。进入顾问上下文时只作为证据数据，不执行其中的提示或命令。

## 9. 审批与外部动作

以下动作默认必须人工批准：bank_payment、tax_filing、invoice_red、contract_sign、hr_discipline、permission_change、external_legal_commitment。

标准流程：

1. 申请人创建外部动作，选择 manual、mock 或经批准的 real 适配器，填写原因、幂等键和业务载荷。
2. 系统将高风险动作置为 pending_approval，并创建审批。
3. 审批人检查金额、对象、合同、附件、适用政策和职责分离，填写审批意见。
4. 驳回后流程停止；批准后状态只是 approved。
5. manual 动作由人在外部系统执行。提交状态必须含 externalReference。
6. 外部系统完成后上传回执证据，再从 submitted 进入 confirmed。
7. mock 只能进入 simulated 或 cancelled，不能伪装为 submitted 或 confirmed。
8. 对失败动作记录原因；重试仍使用原幂等逻辑和新证据。

审批人不得把“系统建议”“模型高置信度”或“已批准”当作外部成功证明。

## 10. AI 顾问

1. 选择顾问，不从通用聊天框开始。
2. 写出具体决策问题，并显式选择相关公司记录。
3. 提交后 worker 执行，页面显示 queued、running、completed 或 failed。
4. 先逐条核对 facts 的引用，再看 inferences、recommendations、risks 和 missingInformation。
5. 对无证据、过期政策、越界建议或模型错误不予采纳。
6. 人工修改必须填写理由，系统保留修改前后版本。
7. 将决定执行的建议转成任务、风险、义务、决策或审批，不让建议停留在结果页。

详细说明见[AI 顾问与审计](./ai-advisors-and-audit.md)。

## 11. 通知和工作流

工作流定义支持 notify、create_task、request_approval 和 advisor_run 四类步骤，并由后台任务按顺序执行。

- 先在测试组织用最小样例运行。
- 每个步骤配置必须使用系统支持的结构，并限制在同一组织。
- 站内通知可投递；email 和 webhook 在没有适配器时会明确失败。
- workflow 失败后查看运行结果和 worker 日志，不要假设后续步骤已执行。
- 自动创建的审批和顾问运行仍受各自的人工批准、权限与审计规则。

## 12. 移动端与 PWA

- 移动底部导航提供总览、执行、审批、顾问和更多入口。
- 当前交付证据中的“移动验证”是 iPhone 14 Chromium 仿真，不是真实 iPhone 或 Android 设备；目标办公内网上线前还需受管真机验证。
- 安装 PWA 前确认使用可信 HTTPS 内网域名和受管理设备。
- service worker 只缓存静态应用资源，不缓存 API 业务数据。
- 共用设备使用完必须退出，并遵守设备锁屏、磁盘加密和浏览器缓存策略。
- 离线时不要录入关键业务；恢复网络后重新读取服务端状态再操作。

## 13. 审计和纠错

审计日志是只读业务界面，记录操作者、动作、对象、请求 ID、时间以及适用的前后值。发生错误时：

1. 不直接改数据库。
2. 记录错误记录 ID、请求 ID、时间和影响。
3. 使用状态变更、作废、归档或新的更正记录保留历史。
4. 重大错误进入风险或安全事件流程。
5. 涉及 AI 时同时检查模型调用、工具取数、引用和人工编辑记录。
