# AI 顾问与审计指南

## 1. 顾问不是通用聊天框

每次运行都必须选择一个业务顾问、提出具体问题，并显式选择公司记录作为上下文。系统不会默认把整库数据发送给模型，也不会允许顾问越过发起人的读取权限。

运行默认仅发起人可见。member 只能在列表、详情和人工修改接口访问自己发起且当前仍具备权限的运行；admin/owner 可凭 `advisor-runs:read-all` 或 `*` 跨发起人读取，但仍必须拥有该顾问的 requiredPermission 和运行中每个上下文资源的 `:read` 权限。`read-all` 不扩大业务数据权限；任一条件不满足时接口按 404 返回，避免泄露运行是否存在。人工修改使用同一可见性规则。

顾问输出必须包含六个结构：

1. facts：带公司记录引用的事实。
2. inferences：写明依据和单项置信度的推断。
3. recommendations：动作、理由、风险和优先级。
4. risks：严重程度和缓解措施。
5. missingInformation：影响判断的缺失信息。
6. confidence 与 disclaimer：整体置信度和适用边界。

没有证据引用的内容不能放入 facts。

## 2. 七类顾问及最大数据范围

实际运行还受用户权限和当前提示词版本限制，下表只是代码策略允许的最大范围。

| 顾问 | 适用问题 | 最大数据范围 |
| --- | --- | --- |
| 总经理 | 跨部门优先级、目标和决策 | 目标、项目、任务、决策、义务、风险、合同、收支、现金流、产品、机会 |
| 财务 | 收支、发票、现金缺口 | 收支、发票、现金流、合同、目标 |
| 法务合规 | 合同、义务、来源适用性 | 合规知识、合规日历、义务、风险、合同、决策 |
| 产品研发 | 产品组合、交付和技术风险 | 产品、项目、任务、决策、GitHub 情报、风险 |
| 市场机会 | 线索、方案和商业优先级 | 机会、产品、合同、目标、决策 |
| 人力行政 | 工作负荷和行政事项 | 目标、项目、任务、义务、风险 |
| 信息安全 | 安全风险、控制和外部技术信号 | 风险、合规知识、合规日历、GitHub 情报、审计事件 |

用户还必须拥有该顾问的入口权限。例如财务顾问要求 financial-entries:read，法务合规要求 compliance-items:read。

## 3. 一次运行的审计链

### 发起前

- API 验证 advisor-runs:create。
- 验证用户具备顾问要求的权限。
- 对每个上下文引用同时检查顾问范围、用户 read 权限、组织归属和资源类型。
- 合规来源只有 `status=active`、`reviewStatus=reviewed`、`nextReviewAt` 尚未到期，并且同时存在确定结论、复核人姓名/角色/机构、胜任依据、明确缺失信息、已上传证据引用、站内登记人、登记时间和锁定来源版本时，才进入模型上下文。只有旧 `reviewed` 字样或部分字段的 legacy 记录会 withheld；后台扫描是否及时运行不会放宽请求时的 fail-closed 判断。
- 对带 `sourceId` 的 obligations 或 compliance-events，系统还会读取被链接来源并继承完整 provenance、active/reviewed/未来复核日门禁；只有来源结论为 `applicable` 时，关联义务或事件才可进入上下文。`not_applicable` 来源本身可以作为被复核事实，但不能证明关联义务；来源缺失、未复核、非 active、无完整 provenance、结论不适用、未安排复核或已过期时，关联内容会 withheld。没有 `sourceId` 的内部公司义务不因缺少来源自动被扣留；compliance-event 自身还必须为 reviewed。`evidenceFileId` 是完成凭证引用，不替代来源适用性复核。
- 固定本次 active 提示词版本，并保存上下文快照。

### 运行中

- 创建 advisor_run 和 company_data.read 工具调用记录。
- worker 创建模型调用记录，保存供应商、模型、提示词版本、请求载荷、状态、耗时和 token 用量。
- 公司记录内容被标记为不可信数据，不能作为模型指令。
- 结构化结果通过 schema 校验。
- facts 中的证据必须来自本次权限过滤后的上下文，否则整次运行失败。

### 完成后

- 保存原始响应、结构化输出、整体置信度和引用。
- 写入 system actor 的完成或失败审计事件。
- 详情接口返回 run、modelCalls、toolCalls、citations 和 edits。
- 人工修改使用乐观并发版本，保存 before、after、编辑人和 reason，并另写 human_edit 审计事件。

因此“页面当前显示内容”不是唯一证据。复核时必须查看该运行的原始模型调用和后续人工编辑。

## 4. 如何提出可审计问题

好的问题包含决策、时间范围和希望比较的对象，例如：

- “依据这份合同、未来 13 周现金流和三项义务，未来 30 天最需要处理的三个风险是什么？”
- “比较这两个产品和相关机会，给出继续、暂停或验证的建议，并列出仍缺少的数据。”
- “根据这个项目、任务和 GitHub 安全情报，判断本周发布是否应推迟。”

不要要求模型“查看公司所有信息”“直接决定是否签署”“自动付款”或“保证合法”。上下文越少越容易遗漏，越多则增加隐私和噪声；只选支持本次判断的记录。

## 5. 结果复核顺序

1. 身份：顾问类型、问题、发起人和运行时间是否正确。
2. 范围：上下文引用是否都是本次希望披露的记录。
3. 事实：逐条打开 sourceType 和 sourceId 核对，不接受孤立摘录。
4. 时效：合规、合同、现金和 GitHub 信息是否仍然有效。
5. 推断：basis 是否足以支持 claim，置信度是否合理。
6. 建议：是否说明风险、成本、依赖和不可逆性。
7. 缺失信息：先补关键事实，再运行一次，不用人工想象补齐。
8. 落地：把采纳项转为系统记录并由人负责。

整体 confidence 只表示模型对当前上下文的自评，不是准确率、法律效力或执行授权。

## 6. 提示词版本管理

管理员可为每类顾问创建新提示词版本。新版本必须：

- 说明用途、输出结构和禁区。
- dataScopes 不超过顾问策略最大范围。
- 保留旧版本，不覆盖历史运行引用。
- 在非生产数据上验证事实/推断分离、引用约束、注入防护和失败处理。
- 记录变更原因、审阅人和启用时间。

启用新版本只影响后续运行，历史结果仍指向原 promptVersionId。

## 7. 人工修改

允许修改已完成的结构化输出，适用于：

- 修正明显事实错误或过时表述。
- 补充专业复核意见。
- 调整建议优先级或风险描述。
- 删除不应继续展示的敏感内容。

修改时必须填写具体原因，不能写“优化一下”。原始模型输出和所有编辑版本必须保留。对重大结论，优先新增专业意见或重新运行，避免让人工改写看起来像模型原始答案。

## 8. 数据与隐私边界

- 默认 mock 提供商只用于流程演示，不能当作真实顾问能力验收。
- 配置真实 LLM 前，确认供应商、处理地域、保留策略、训练用途、分包商、删除能力和事件通知。
- `LLM_BASE_URL` 必须是经批准的 HTTPS 地址；HTTP（包括生产环回地址）会被拒绝，模型调用不会跟随供应商重定向。
- 不发送无关个人信息、身份证件、银行账号、未公开商业秘密或整份文件。
- 必要时先创建脱敏摘要作为上下文，并保留摘要来源和审阅人。
- LLM_API_KEY 只进入运行环境密钥，不写入仓库、提示词或审计载荷。
- 真实模型连接失败必须显示 failed，不回退成未标识的 mock 结果。

## 9. 工具与外部动作边界

当前顾问工具记录主要表示对已授权公司记录的读取。模型不能通过顾问运行直接付款、报税、红冲、签署、处分、改权或作出对外承诺。

如果建议需要外部执行：

1. 人工把建议转成任务、决策或 external action。
2. 高风险类型自动进入审批。
3. 批准后由人工或经单独批准的适配器执行。
4. 回执确认与顾问运行分别审计。

模型输出永远不是批准记录或外部回执。

## 10. 故障与异常处理

| 现象 | 处理 |
| --- | --- |
| queued 长时间不动 | 检查 worker、pg-boss 和 ready 健康状态 |
| failed | 查看模型调用错误；不要反复提交敏感上下文 |
| 引用被拒绝 | 检查用户权限、顾问范围、组织和资源 ID |
| 合规内容 withheld | 完成人工复核，确认 reviewed、active 且下次复核日在未来，而非绕过过滤 |
| 事实无有效引用 | 不采纳；补充上下文或报告提示词缺陷 |
| 输出疑似提示注入 | 保全运行 ID，停止使用结果并按安全事件处理 |
| 人工修改冲突 | 重新读取最新 version 后比较，不覆盖他人修改 |

安全威胁及响应见[威胁模型](../security/threat-model.md)和[事件响应](../security/incident-response.md)。

## 11. 审计抽查

每月至少抽查：

- 七类顾问是否都只使用允许范围。
- 模型供应商和模型名称是否与批准配置一致。
- promptVersionId 是否可追溯到未修改的历史版本。
- toolCalls 和 citations 是否与 contextSnapshot 一致。
- 合规来源是否在运行时为 reviewed、active，且 `nextReviewAt` 非空并晚于当前时间；带 `sourceId` 的义务和合规事件是否正确继承该门禁，worker 是否运行不影响此 fail-closed 判断。
- 抽查同组织不同发起人的运行：member 应无法在列表、详情或人工修改接口看到他人的运行；admin/owner 的 `read-all` 仍应在缺少顾问 requiredPermission 或任一上下文 `:read` 时返回 404。
- 人工 edits 是否有真实理由和编辑人。
- 高风险建议是否经过独立审批和外部凭证确认。
- 日志和模型载荷是否出现不必要的个人信息或密钥。
