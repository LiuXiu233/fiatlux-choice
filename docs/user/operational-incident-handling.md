# 运行异常人工处置指南

## 适用范围

“运行异常处置”只汇总后台 worker 写入 **lease_expired** 的三类记录：

- AI 顾问运行；
- 工作流运行；
- 数据库备份运行。

租约失效表示先前执行者长时间没有完成，且重复投递已经被系统关闭为 **failed**。模型可能已经收到请求，工作流可能已经创建部分子记录，备份命令也可能留下归档或临时文件。因此它不是“可以安全重试”的信号。

一般业务校验失败、队列入队失败和通知投递失败仍在各模块及审计日志中查看，不会因为名称相近自动进入本页。

## 权限

- owner 的全局权限可以查看和处置。
- admin 需要 **operations-incidents:read** 与 **operations-incidents:update**。
- member 与 viewer 默认不可查看，直接请求 API 也会被服务端拒绝。

既有部署升级到包含这两个权限的版本后，不能用日常 **metadata-only** seed 静默修改角色。负责人须先批准关键权限变更，再按管理员手册执行一次 **system-role-maintenance**，核对逐项审计。

## 每次处置步骤

1. 打开“系统 → 运行异常处置”，默认查看“待人工处置”。
2. 记录事件 ID、失败运行 ID、当前状态和版本。若来源记录缺失，停止关闭并按数据完整性事件升级。
3. 打开对应顾问、工作流或备份记录，再打开审计日志。核对触发者、开始时间、模型/工具调用、工作流 checkpoint、目标子记录、备份目录、对象或外部系统状态。
4. 系统显示“已记录部分结果”时，逐项核对并建立人工补偿任务。该提示只代表数据库已经看到部分结果；显示“未记录”也不能证明外部没有副作用。
5. 选择一种结论：
   - “调查后未发现部分副作用”：仅在证据支持没有部分结果时使用。
   - “已完成并核对人工补偿”：已有数据库 checkpoint、模型输出或备份产物时必须使用，并填写补偿主记录引用。
6. 填写至少 20 字的调查说明和至少一条稳定证据引用。证据可以是审计事件 ID、工作日志、任务 ID、新备份运行 ID、受控归档或经批准的外部回执；不得粘贴密码、Cookie、token、密钥或完整敏感内容。
7. 确认“旧运行不会自动重放”。提交成功后到“已记录处置”复核处置人、时间、说明和证据。

## 提交后的真实状态

处置 API 只追加一条 **manual_review_completed** 审计：

- 原顾问、工作流或备份记录仍保持原状态、版本、错误和 partial output；
- 不调用 LLM；
- 不执行工作流步骤；
- 不发送 pg-boss job；
- 不运行备份命令；
- 不把人工说明显示成原运行成功。

同一个租约事件通过事件 UUID 的数据库事务锁只能关闭一次。并发或重复提交返回 409。该锁不修改审计事件；跨组织事件按不存在返回 404。

如需重新完成原业务，先创建新的任务说明原因，再从对应模块建立一个新的顾问、工作流或备份运行。新运行必须有自己的 ID 和审计，不得修改、复用或重放旧失败记录。

## 不能据此声称的事项

- “处置完成”不等于原运行成功。
- “未记录部分结果”不等于外部没有副作用。
- “人工补偿完成”是操作人基于所填证据作出的内部声明，系统不能自动验证外部日志、文件或业务判断的真实性。
- Web 数据库备份只覆盖 database-only job；完整灾备、partial 清理和恢复仍按管理员备份恢复手册执行。
- 对外付款、签署、报税、红冲、人事处分或法律承诺仍必须走各自人工审批和真实外部回执，不能用运行异常处置替代。
